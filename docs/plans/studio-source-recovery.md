# Studio input and recovery integrity (round 36)

A native-browser reproduction found that pasted NUL characters could enter the editor and be saved to IndexedDB with a successful recovery status. Reload then rejected that source as binary. The stored record survived, but the screenplay appeared blank and ordinary reopening and Studio backup creation could not recover it.

`sourceEditProblem` now guards editor transactions before they enter history or recovery. It retains the existing 500,000-character and 20,000-line limits and scans only newly inserted text for NUL. An invalid replacement or multiple-change transaction is rejected in full, with an explanation; existing text, selection and undo history remain intact. It never strips characters. Other Unicode, private text, BOM and normal CodeMirror newline handling remain supported. Lone UTF-16 surrogates remain editable and JSON-backup-capable; the separate lossless UTF-8 download guard still prevents silent text-file conversion.

For legacy saved records, the recovery library validates source only after the user selects Open. Invalid source stays stored unchanged and the current editor is not replaced. An explicit **Download recovery JSON** action appears for that chosen record, with a warning that it includes private text and is for manual recovery, not a normal importable Studio backup. The `voxdown-studio-raw-recovery` version-1 JSON envelope contains only the saved name and exact source; JSON escaping preserves NUL, BOM, line endings and unpaired surrogates. A portable `.recovery.json` filename avoids confusing it with `.studio.json`. No automatic downloads, source sanitization or saved-record deletion occurs. Closing or refreshing clears the captured recovery source. Normal library listings remain metadata-only.

Verification includes five transaction tests, two browser library regressions, and three actual-app browser flows: NUL replacement rejection followed by undo/redo and reload; downloading an unchanged legacy invalid record; and independent edits/reloads in two tabs. The latter confirms recovery edits receive distinct draft IDs. Existing storage transaction, denied-storage, quota, timed-out-save and stale-write checks remain relevant; these changes do not promise that the browser can finish a write after abrupt process termination. Physical iOS composition, tab discard and storage pressure remain device gates.
